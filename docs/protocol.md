# 通信与模块契约

状态：契约设计草案，尚无已发布 wire 协议。字段命名、编码格式和通道名需在实现前冻结；兼容性通过版本声明与客户端、服务端契约测试验证。

## 1. 数据路径

```text
服务端 UI 消息
  → 宿主网络适配器
  → 框架校验与路由
  → 所属模块更新状态或处理事件
  → 窗口与 HUD 订阅状态

窗口 / HUD 操作
  → 模块生成类型化请求
  → 框架请求出口
  → 宿主网络适配器
  → 服务端业务处理
  → 结果与权威状态回传
```

统一入口只接管声明属于框架及业务 UI 的消息，不截获所有 Minecraft 网络包。模块不各自注册同一网络 receiver。框架通过公开的传输与编解码接口接入服务端，宿主适配器负责在网络协议与框架消息之间转换，不要求接入方使用特定的序列化库或服务端实现语言。

接入已有网络栈时，在既有 receiver 内增加适配调用，同一消息只经过一条状态写入路径。适配器须保留请求关联、对象身份、版本和服务端会话含义，不能在 UI 层重新生成业务 session token。

## 2. 连接与能力协商

客户端安装的模块集合在启动后确定，每次连接进行兼容性检查：

- 客户端声明框架协议版本，以及每个模块支持的消息契约版本。
- 服务端返回接受的能力集合、版本及必需能力。
- 必需模块缺失或版本没有交集时返回明确诊断，不开放相应会话；如果是进入服务器所必需的能力，则连接检查失败。
- 可选模块缺失时服务端不再向它发送订阅数据，客户端入口显示不可用或隐藏。

模块能力只描述客户端能理解什么，不代表它获得权限。服务端仍须校验玩家身份、物品归属、距离、会话有效性、库存事务及动作参数。

兼容检查必须在使用相关协议前完成。接入不支持能力协商的服务端时，宿主适配器必须显式声明已验证的能力与协议版本，不把“没有握手消息”误判为全部功能可用。

## 3. 消息契约

每种消息登记方向、所属模块、稳定消息 ID、版本、类型化载荷和处理语义。载荷由该消息的 schema 定义，不使用任意 `Map<String, Object>` 作为公共业务协议。

| 消息类别 | 服务端输入语义 | 客户端处理 |
|---|---|---|
| 完整快照 | 对象或状态流的完整权威状态及 revision | 原子替换对应状态，再通知订阅者 |
| 增量 | 目标流、base revision、new revision 与变更 | 仅在基准匹配时应用，否则请求完整快照 |
| 事件 | 已发生且不一定能从快照重建的事实 | 按契约决定顺序和去重方式，不用事件伪造完整状态 |
| 请求结果 | 原 request ID、成功或业务拒绝、错误信息 | 完成对应请求，状态更新仍遵循快照或增量契约 |
| 会话状态 | 某业务会话创建、更新、失效或关闭 | 模块处理该会话，失效后禁用旧操作 |

逻辑信封至少能表达目标模块、消息类型和协商版本。请求具有关联 ID；涉及对象或会话的消息具有明确身份；快照和增量带状态流及 revision。并非每类消息都携带所有字段。

连接代数由客户端运行时维护，异步任务携带所属代数；断线或切服后，旧连接排队的消息不得写入新状态。它不替代服务端会话身份。

收包线程可以完成受限的解码与校验，状态提交及 UI 通知通过约定的客户端执行器串行执行，不能在网络线程直接操作 owo 控件。

## 4. 请求出口

子模块提交自己登记过的请求类型；框架检查来源模块是否启用、该请求是否允许向服务端发送、载荷是否合规及连接是否有效，再交给网络适配。

一次请求至少区分：本地拒绝、已发送、等待结果、服务端接受、服务端拒绝、超时、连接结束。实际 API 可合并中间通知，但不能把“写入网络发送队列”当作“业务成功”。

超时不证明服务器没有执行。库存移动、分堆、消耗等有副作用的请求不得自动重发，除非该请求契约明确支持幂等键。超时后重新同步权威状态；迟到结果不能重复触发动作完成副作用。

请求结果与状态更新的先后关系必须由每种请求契约规定。成功结果若先于库存快照到达，不以本地猜测替代最终库存。多个窗口和 HUD 消费同一份已提交的库存状态。

## 5. 模块路由与错误

一条领域消息具有明确的接收模块，不向所有窗口广播原始网络包。跨模块共享通过已声明的状态接口进行；多个视图订阅同一状态不等于多次应用库存增量。

| 诊断 | 行为 |
|---|---|
| `MODULE_MISSING` | 记录目标模块和消息 ID，不能当作已消费；按必需或可选能力处理 |
| `PROTOCOL_MISMATCH` | 停止分发不兼容消息，给出双方支持版本 |
| `UNKNOWN_MESSAGE` | 记录未知契约，不进入任意业务处理器 |
| `INVALID_PAYLOAD` | 拒绝该消息，保留最后一份有效状态 |
| `STALE_CONNECTION` | 丢弃旧连接任务，不改变当前连接状态 |
| `REVISION_GAP` | 暂停应用该流增量，请求完整快照 |
| `REQUEST_TIMEOUT` | 清理等待状态并同步，不能显示成功或自动重复消耗 |
| `HANDLER_FAILURE` | 隔离故障模块的本次处理，报告错误，必要时停用相关功能并重新同步 |

错误包含可定位的模块、消息、协议版本及请求 ID，不展示原始载荷中的私人数据。重复错误聚合，避免每帧弹窗。只有已协商的诊断消息才可回传服务端，未知消息不会导致无限互相报错。

## 6. 最小验收链路

1. 服务端发送完整库存快照，框架交给库存模块，背包窗口和 HUD 显示同一 revision。
2. 用户拖动物品，模块提交移动请求，框架保留关联关系并发送。
3. 服务端拒绝请求时显示原因，移除拖放临时态，物品不在客户端凭空消失。
4. 服务端接受并更新状态后，所有视图一致刷新。
5. 缺少必需库存模块时，在功能启用前明确失败；缺少可选模块时，其余功能继续工作。
6. 断线重连、旧消息迟到、增量缺口和请求超时均不产生跨连接污染或重复事务。
