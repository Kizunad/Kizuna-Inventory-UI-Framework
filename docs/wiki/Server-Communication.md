# 服务器通信

> 状态：契约设计指南。尚无已发布通道名、编码格式、消息 schema 或网络 SDK。下面的消息名只用于说明接入关系。

## 接入职责

宿主适配器连接游戏网络栈与框架消息接口。模块登记自己接收的消息和允许发送的请求，框架统一校验与路由。统一入口只处理已登记的 UI 消息，不接管全部游戏网络包。

服务端可以使用不同语言和实现。它必须提供对应契约的业务处理、结果和状态同步，不能把客户端声明的模块能力当作权限证明。

## 一个库存模块的输入输出

以下为概念示例，实际 ID、版本、字段及编码需由已发布的消息契约确认：

| 方向 | 示例消息 | 必须说明的语义 |
|---|---|---|
| S2C | 库存完整快照 | 状态流身份、完整状态和 revision |
| S2C | 库存增量 | base revision、new revision 与变更 |
| C2S | 移动物品请求 | request ID、实例身份、来源、目标及数量 |
| S2C | 请求结果 | 原 request ID、接受或拒绝及原因 |
| C2S | 请求重新同步 | 目标状态流及当前已知 revision |

为每种消息声明目标模块、稳定消息 ID、方向、兼容版本和类型化载荷。请求结果与库存更新的先后关系必须写入契约，不能让视图猜测成功结果是否已经包含新状态。

## 连接流程

1. 客户端声明框架协议版本和已安装模块的通信能力。
2. 服务端返回协商版本、接受的能力和必需能力。
3. 必需模块缺失或版本无交集时明确失败；可选模块缺失只关闭对应能力。
4. 完成协商后订阅状态并开放相关操作。
5. 断线时使旧连接任务失效，清理会话、订阅及未完成请求。

若对接不支持握手的既有服务端，宿主必须显式声明已验证的能力及协议版本，不能把没有握手响应当作自动兼容。

## 分发与结果

一条状态消息只由所属模块应用一次，再通过共享状态通知多个视图。框架不得为了更新多个窗口而多次执行同一库存增量。

解码后在约定的客户端执行器上提交状态。增量基准不匹配时请求完整快照；旧连接消息不得写入当前连接。未知消息、无效载荷、缺失模块和版本错误应形成结构化诊断。

请求需区分本地拒绝、已发送、等待结果、服务端接受、服务端拒绝、超时和连接结束。超时不证明服务端没有执行；有副作用的请求仅在契约支持幂等键时才允许自动重试，否则先同步权威状态。

服务端必须独立校验玩家身份、物品归属、距离、会话、容量和业务规则。UI 中禁用按钮只提供反馈，不替代权限校验。

完整设计见[协议设计](https://github.com/Kizunad/Kizuna-Inventory-UI-Framework/blob/main/docs/protocol.md)。排错入口：[故障排查](Troubleshooting.md)。
