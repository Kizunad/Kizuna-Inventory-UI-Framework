# 文档维护

## 唯一编辑来源

Wiki 正文维护在主仓库的 `docs/wiki/`，通过普通提交和评审更新，再发布到 GitHub Wiki。不要在网页编辑器中长期维护另一套正文。Wiki 尚未初始化时，可以在网页创建一个占位首页，后续由同步工具替换。

主仓库 README 链接到 Wiki。Wiki 面向接入者提供教程与排错；`docs/architecture.md`、`docs/protocol.md` 和 `docs/roadmap.md` 记录设计与实施范围。

## 随变更更新

修改以下内容时，在同一提交中检查对应 Wiki 页面：

| 变更 | 文档 |
|---|---|
| 依赖、初始化、产物 | 接入指南、版本与兼容性 |
| 模块注册、窗口生命周期 | 模块与窗口扩展 |
| 库存模型、拖放、状态订阅 | 库存与状态 |
| HUD 或动态槽位 | HUD 与槽位栏 |
| 主题、背景、资源重载 | 主题与背景 |
| 协议、请求结果、能力协商 | 服务器通信、故障排查 |
| 新发布或破坏性变更 | 版本与兼容性及相应教程 |

未实现的接口标为设计草案；已发布的示例必须注明适用版本，并由对应版本的构建或示例测试验证。不得把概念说明写成看起来可以直接编译的虚构 Java API。

## 检查与发布

在主仓库根目录运行：

```bash
python3 scripts/wiki.py check
python3 scripts/wiki.py publish
```

检查命令验证必需页面、页名、代码块闭合和本地文档链接，CI 会执行相同检查。发布命令要求源工作区干净及 Git 具有 Wiki 写权限；不会打印或保存认证令牌。

发布工具克隆 Wiki 仓库，将页面间 `.md` 链接转换为 Wiki 页面链接，只提交有内容变化的受管页面，然后普通推送。它不会强推，也不会删除 Wiki 中来源不明的页面。重复执行无变更时不创建提交。

如果 GitHub 尚未创建 Wiki Git 仓库，先在仓库 Wiki 的网页界面创建 `Home` 页面，再重新运行发布命令。GitHub Wiki 没有与普通仓库 Contents API 等价的页面创建接口；启用 Wiki 开关不一定同时创建 Git 仓库。

推送冲突时重新运行以获取最新 Wiki。若有人直接修改了受管页面，先将需要保留的内容合回 `docs/wiki/` 再发布。移除或重命名页面时同步更新链接，并单独审阅远端旧页面的清理。
