# 实施顺序与验收

当前已完成仓库创建和初始设计，以下实现均未完成。主屏视觉方案仍待用户评审，注册和通信边界先行。

## 第一阶段：可独立构建的基础 API

- 建立 Java 17 构建、框架 JAR 产物和最小 Fabric 演示宿主。
- 实现模块身份、版本检查、依赖校验以及原子注册。
- 确定功能、窗口、HUD、槽位栏、主题和背景的最小类型化接口。
- 复用经过核验的状态订阅、动作出口、窗口生命周期和逻辑视口约束。

验收：框架不依赖 Bong 即可构建；演示子 JAR 通过公开 API 注册，缺失依赖、重复 ID 和不兼容版本返回可定位错误。测试保护模块隔离与生命周期契约，不绑定私有字段或源码拼写。

## 第二阶段：主屏与动态注册演示

- 实现功能目录及窗口栏，单例、按对象分实例、最小化和聚焦行为明确。
- 接入两个演示窗口、两种不同数量的槽位栏、共享状态的 HUD。
- 注册默认主题和背景，验证主题切换、资源重载与回退。
- 交付实际运行截图与交互预览，由用户确认布局后再深化视觉实现。

验收：新增演示功能、HUD 或背景仅修改演示模块；框架无需新增业务枚举。工作台关闭后 HUD 正常显示，分辨率或 GUI scale 改变时输入命中与绘制一致。

## 第三阶段：通信与库存契约

- 冻结首版模块协商、消息、请求结果和错误协议。
- 通过可控的模拟传输验证完整快照、增量、拒绝、超时和旧连接消息。
- 实现通用库存显示模型、拖放、旋转、分堆及槽位绑定意图。

验收：一个共享库存状态驱动主屏和 HUD；服务端拒绝或超时不造成物品丢失；增量缺口触发重新同步；模块不存在时不会静默吞消息。真实接入完成前不声称实现了 Bong 服务端兼容。

## 第四阶段：Bong 增量接入

- Bong 通过依赖使用框架 JAR，提供现有协议与框架 API 的转换。
- 先接入库存工作台和一个 HUD，保留服务端库存权威与既有协议身份。
- 依次注册物品详情、修习、身体、炼丹和锻造等子功能。
- 新路径验收后才移除对应旧实现，避免两套 receiver、状态写入或输入捕获并存。

验收：Java 17 客户端门禁通过；真实服务端往返覆盖移动、分堆、拒绝、断线重连及模块能力；视觉评审通过。提取已有源码或资源前核对原许可证和来源，保留必要声明。

## 第五阶段：首版发布

- 发布可供消费者引用的版本化 Maven 产物和 Fabric 运行 JAR。
- 写明 Minecraft、Fabric、owo、框架 API 和模块协议的兼容范围。
- 提供子 JAR 接入示例、迁移说明及公开 API 的兼容策略。

验收：干净环境可独立构建；示例子 JAR 只依赖已发布 API；Bong 可固定版本消费；新增业务窗口、HUD、主题无需修改框架源码。
